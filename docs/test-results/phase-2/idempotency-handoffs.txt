### R1 — `C-HANDOFF-6` NaN/Infinity and `C-HANDOFF-7` tag dedupe (`internal/store/handoff_test.go`)

`TestHandoffValidationMatrix` gained three sub-cases, all inside the existing test:

| sub-case | rule | assertion |
|---|---|---|
| `confidence is 1e400 (overflows float64)` | `C-HANDOFF-6` | `400 handoff_invalid`, `details.field = memory_writes[0].confidence`, 0 handoff rows, 0 outbox rows |
| `confidence is -1e400 (overflows float64)` | `C-HANDOFF-6` | same |
| `tags dedupe keeps first-seen order` | `C-HANDOFF-7` | stored document `memory_writes[0].tags == ["a","b"]` and outbox `tags_json == ["a","b"]` for an input of `["a","b","a"]` |

JSON cannot spell `NaN` or `Infinity`, so the two arms the rule names are reachable only the way a
wire reaches them: `1e400` / `-1e400` are syntactically valid JSON numbers that overflow `float64`.
`json.Marshal` refuses `math.Inf`, so the body is built as a raw string (a Go map cannot express what
a client can send). `checkJSONNumber` catches the overflow via `strconv.ParseFloat`'s range error
before the typed decode, which is why the rejection names the field rather than reporting a generic
"cannot unmarshal" document error. `validateMemoryWrite`'s `math.IsNaN`/`math.IsInf` guard remains
unreachable through any transport (review observation 6) — it is the guard that makes the rule true
for a Go caller, and these two sub-cases are what prove the transport-visible behaviour.

### R3 — `claim.pre_commit` now fires *after* `insertAudit` (`internal/store/claim.go`, both call sites)

`claimInTx` and `claimNextInTx` previously fired `crashpoint.ClaimPreCommit` before the `claimed`
audit row was written, so `TestIdempotencyCrashAtomicity`'s "no audit row survived" assertion could
not fail no matter what the audit path did. The call now sits after `insertAudit` in both functions —
still inside the transaction, still before `COMMIT`, so the point keeps its name and its meaning —
which is also where `handoff.pre_commit` already sat.

**Verification that the assertion is now real (negative control, scratch copy, never committed).**
The point is now after the write, so a passing "0 audit rows" no longer distinguishes "the rollback
removed it" from "it was never written". A counterfactual run proves which it is: copy the tree to
`/tmp/negctl`, replace the SIGKILL in `crashpoint.fire` with a `return` so the transaction *commits*
at exactly the same call site, and run the pre-commit leg.

```
$ cd /tmp/negctl && go test ./internal/store/ -count=1 -run 'TestIdempotencyCrashAtomicity/pre_commit' -v
        Error Trace:    /tmp/negctl/internal/store/idempotency_test.go:425
        Error:          Not equal:
                        expected: int(0)
                        actual  : int64(1)
        Messages:       iteration 0: no key row (C-IDEM-13a)
        Error Trace:    /tmp/negctl/internal/store/idempotency_test.go:426
        Error:          Should be false
        Messages:       iteration 0: no mutation
        Error Trace:    /tmp/negctl/internal/store/idempotency_test.go:427
        Error:          Not equal:
                        expected: int(0)
```

So at the instant `claim.pre_commit` fires, the key row, the mutation **and** the audit row are all
staged in the open transaction. Under the real SIGKILL all four assertions report 0 (below), which
means the rollback — not the absence of a write — is what leaves nothing behind. That is the
`C-AUDIT-4` claim, and it is now falsifiable: the same assertions fail the moment the transaction is
allowed to commit. The scratch copy was deleted; nothing from it is in this commit.
